## Persistence boundary

- `src/auth.tsx` calls Supabase Auth for email/password signup, login, session loading, and sign-out. The account-created trigger in `supabase/migrations/20261010194129_auth_only_lucid_schema.sql` creates the public profile. The old `Auth` component in `onboarding.tsx` is not routed by `main.tsx`.
- `src/state.tsx` calls `saveAccountTrip`, `loadAccountTrips`, and `deleteAccountTrip` for signed-in account trips. Sample trips and Maya's standalone demo bypass those server writes.
- `src/account-trips.ts` sends complete account trips through validated transactional RPCs. Event submissions enter the queue before optional address lookups; later map matches only update the unchanged address. Root fields, event attendees, guest roles/days, preferences, budgets, expense shares/repayments, reminders, and dismissed IDs persist in normalized tables. The owner manages roles, invitations, group settings, and budgets. A shared save checks current membership, revision, and exactly which records changed. Editors may change events and reminders; Day Editors need permission on both the original and destination dates. Viewers cannot change either. Accepted travelers may still manage their own survey, expenses, and individual budget. Guest planner IDs never grant Auth-account membership.
- `mutate` and `updateTrip` enqueue account trip changes immediately. The save queue serializes edits, resumes recovered drafts on startup and retries temporary failures on reconnect or with backoff, and reports confirmed database status. Browser storage contains demo data plus temporary pending recovery; successful account trip copies are removed. All visible account screens check for database changes every five seconds and on focus or reconnect, without replacing pending edits.
- `tripFromRow` treats full database bundles as authoritative. A metadata-only legacy trip can import old browser details once, only when the database already assigns that trip to the signed-in account. Legacy IDs and historical traveler references are preserved through remapping.

## Rules for later work

1. Follow the handler to its actual network call. A toast saying “saved,” “connected,” or “invited” is not proof of a server write.
2. Do not infer database authorization from the local participant selector, role flags, or matching email addresses.
3. Before marking a feature server-backed, add its persistence/integration and verify reload plus a fresh browser/account where applicable, including failed writes and permission checks.
4. Update this file and the nearby source comments with that feature. Keep ordinary validation, save-failure recovery, unavailable-action feedback, and clearly named sample actions in the UI. Hide implementation notes only on Budget and Suggestions; preserve the other pages and dialogs, including their shared footer.

## Seven-day itinerary calendar

The itinerary can display a list or a seven-day time grid. Calendar drag/drop and the keyboard/touch Move dialog change the same event date/start/end fields through `updateTrip`, the existing save queue, and Supabase `save_trip_bundle`. Duration and event metadata are preserved. Existing trip date limits, source/target edit permissions, overlap validation, database ownership and revision conflict checks remain enforced. Failed account writes retain the recovery controls; sample trips stay browser-local. No parallel calendar data store or schema migration is needed.

## Event location search

`EventLocationInput` provides worldwide venue/landmark/street-address suggestions from Photon/OpenStreetMap. Searches use a soft geographic bias for the selected trip stop, then rank matching names by distance. Search near allows another trip stop or Worldwide; no venue results are geographically restricted. Informal directional regions use an approximate parent-region focus, and unresolved destinations fall back to worldwide search. Selected results populate the existing `Event.place` field and persist through the unchanged Supabase save queue and relational event location column. Manual entry is retained; no new API keys, database schema, or device location permissions are needed. This lookup does not provide business reviews, accessibility facts, or restaurant recommendations.
