## Persistence boundary

- `src/auth.tsx` calls Supabase Auth for email/password signup, login, session loading, and sign-out. The account-created trigger in `supabase/migrations/20261010194129_auth_only_lucid_schema.sql` creates the public profile. The old `Auth` component in `onboarding.tsx` is not routed by `main.tsx`.
- `src/state.tsx` calls `saveAccountTrip`, `loadAccountTrips`, and `deleteAccountTrip` for signed-in account trips. Sample trips and Maya's standalone demo bypass those server writes.
- `src/account-trips.ts` sends complete account trips through validated transactional RPCs. Event submissions enter the queue before optional address lookups; later map matches only update the unchanged address. Root fields, event attendees, guest roles/days, preferences, budgets, expense shares/repayments, reminders, and dismissed IDs persist in normalized tables. The owner manages roles, invitations, group settings, and budgets. A shared save checks current membership, revision, and exactly which records changed. Editors may change events and reminders; Day Editors need permission on both the original and destination dates. Viewers cannot change either. Accepted travelers may still manage their own survey, expenses, and individual budget. Guest planner IDs never grant Auth-account membership.
- `mutate` and `updateTrip` enqueue account trip changes immediately. The save queue serializes edits, resumes recovered drafts on startup and retries temporary failures on reconnect or with backoff, and reports confirmed database status. Browser storage contains demo data plus temporary pending recovery; successful account trip copies are removed. Recovery journals use separate records per queue and trip so another tab cannot overwrite or clear an interrupted save. Startup discovers abandoned journals and retains revision checks; competing drafts are never silently merged. All visible account screens check for database changes every five seconds and on focus or reconnect, without replacing pending edits.
- The atomic `save_account_trip` owner RPC saves content, ordered destination zones, and photo credit in one revision-checked transaction. Legacy writers use the same canonical path; missing zones are reconciled by destination identity, and contradictory or unsupported fields are rejected. The bundle reader returns coherent photo metadata without a second client query. See `PERSISTENCE_CONTRACT.md` and the November 9 UTC atomic-save/snapshot migrations.
- Recovery writers hold browser Web Locks for their lifetime. Only abandoned writers may be adopted; malformed or incompatible snapshots are preserved for download instead of loaded. Storage failures show an explicit warning. The exhaustive runtime schemas require a deliberate parser rule when domain fields change.
- `tripFromRow` treats full database bundles as authoritative. A metadata-only legacy trip can import old browser details once, only when the database already assigns that trip to the signed-in account. Legacy IDs and historical traveler references are preserved through remapping.
- Live database check on November 8, 2026: `save_trip_bundle_with_timezones` is missing from the deployed Supabase schema. Apply `supabase/migrations/20261107120000_ordered_destination_timezones.sql` to enable ordered destination time zones. Until then, one-destination owner trips with a matching trip time zone use the existing `save_trip_bundle` RPC; multi-destination trips show an explicit migration error and retain their unsaved draft.
- Destination time zones now use the selected Photon place coordinates and Open-Meteo's coordinate-based zone lookup before falling back to name search. This avoids choosing a same-named town's time zone for a state such as Michigan.

## Rules for later work

1. Follow the handler to its actual network call. A toast saying “saved,” “connected,” or “invited” is not proof of a server write.
2. Do not infer database authorization from the local participant selector, role flags, or matching email addresses.
3. Before marking a feature server-backed, add its persistence/integration and verify reload plus a fresh browser/account where applicable, including failed writes and permission checks.
4. Update this file and the nearby source comments with that feature. Keep ordinary validation, save-failure recovery, unavailable-action feedback, and clearly named sample actions in the UI. Hide implementation notes only on Budget and Suggestions; preserve the other pages and dialogs, including their shared footer.

Itinerary context follows editing location, earlier same-day event, next same-day event, previous-day event, then trip destination. Event bias uses 20 km; destinations use their geographic bounds when available. Optional context and provider requests are independently bounded. Event search never activates the regular Maps key. ## Currency converter

The Budget page previously had no conversion service or currency selector; the ledger stores integer USD cents. `currency-converter.tsx` now provides a standalone 37-currency calculator, initially USD → South Korean won (KRW). It does not change ledger totals, expense history, saved budgets, or database contracts. Values stay in decimal currency units until formatted with each currency's normal minor units.

`exchange-rates.ts` fetches only the selected pair from [Frankfurter v2](https://frankfurter.dev/), a free API requiring no key. Its blended central-bank reference rates update when sources publish, generally on business days; this is not a live trading feed or a bank/card quote. The browser sends currency codes only. No paid service, scheduler, secrets, or database migration is required.

Validated rates are cached per pair in browser storage for seven days. The open page schedules its next refresh for cache expiration; returning to the page or reconnecting reuses unexpired rates. Manual refresh bypasses the application cache. Requests time out after 10 seconds and superseded requests are canceled. A failed refresh may show a saved rate with an explicit warning and its original date/check time, never a fabricated rate. Observations over fourteen days old are rejected; observations over seven days old show an age warning. This allows the weekly refresh cycle plus a limited outage fallback. Weekends and holidays can legitimately retain the last business-day rate. Disabled/corrupt browser storage does not prevent live conversion.

Automated coverage includes numeric validation and currency rounding, invalid/old/mismatched responses, cache expiration, forced refresh, unavailable storage, HTTP failures, pair-switch races, offline fallback/reload, same-currency conversion, automatic weekly renewal, and unchanged USD totals on desktop and mobile. The live provider and published browser flow are checked separately from mocked tests.

Verification on November 10, 2026: 106 unit tests and 168 Playwright checks passed; the production build passed. Real browser requests returned USD/KRW and USD/TWD rates. All 37 offered codes were present in the provider’s live USD feed, and the hosted origin passed CORS. The converter had zero axe WCAG A/AA violations in the mobile check and no horizontal overflow. Browser regression tests use controlled service responses; live provider checks are separate.
